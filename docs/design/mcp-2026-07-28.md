# MCP 2026-07-28: what changes for rote

Status: design, not implemented. Written 2026-10-18.

Scope: every place rote speaks MCP. That covers the OAuth client and token
store (`rote mcp login`), the emitted runtime helpers (Python
`_rote_mcp.py`, TS `_roteMcp.ts`, the Workers helper, and the rote-cloud
binding), park-on-auth on four runtimes, the compiler's live MCP tools,
`eval --run`, and `rote serve` / `rote register`.

Every claim below rests on one of three sources: the spec text, published
package source, or a probe against a live server. Probes and their raw
results are in the appendix so they can be rerun. No probe authenticated to
any account. Client-registration probes were stopped before any request with
side effects was sent.

## TL;DR

1. **Nothing breaks today.** Every public server probed either speaks both
   protocol eras or only the legacy one. rote's current clients (fastmcp 3.4.9
   in Python, `@modelcontextprotocol/sdk` 1.x in emitted TS) call them
   successfully over the legacy handshake (A4, A6).
2. **rote breaks the day a server goes modern-only.** A local modern-only
   server rejects both current clients with `-32022 Unsupported protocol
   version`. fastmcp 4 and the TS v2 client in `auto` mode both succeed (A5).
3. **CIMD-only is not viable.** Of 14 hosted authorization servers probed,
   only 3 advertise CIMD (Linear, Notion, Sentry). Cloudflare explicitly
   advertises `false`. 8 offer only DCR. GitHub, Asana and HubSpot offer
   neither and need a pre-registered client (A1).
4. **rote never uses CIMD, even where it is offered.** `rote mcp login`
   attempts DCR against Linear, which advertises CIMD, because rote passes no
   `client_metadata_url`. Passing one switches Linear to CIMD and leaves the
   other servers on DCR, exactly as the spec's priority order says (A2).
5. **rote does not validate `iss` today.** RFC 9207 checks are a client MUST
   in 2026-07-28. Eight of the 14 probed authorization servers advertise
   `authorization_response_iss_parameter_supported: true`. mcp 1.x does not
   check `iss`. mcp 2.x / fastmcp 4 and TS v2 do.
6. **Two defects surfaced along the way. Neither depends on the spec:**
   - On main, a DBOS step bound to a tool with a typed `outputSchema` fails
     with `PicklingError` (A7).
   - On fastmcp 4, rote's 401 detection stops matching, so park-on-auth would
     silently turn into a plain failure (A8).

   Both are fixed in the fastmcp 4 port, draft PR #103:
   - 401 detection: a response hook on the helper's httpx2 client records
     the 401.
   - Result payload: the helper now returns `structured_content`.
7. **Recommendation: Option A, dual-stack.** Prefer the modern protocol with
   automatic fallback, and order registration as pre-registered, then CIMD,
   then DCR. Most of the work is the fastmcp 4 port plus a TS v2 helper
   migration. Ship it with the era-matrix e2e described below.

## What the spec actually changed

The claims were checked against the 2026-07-28 spec pages and changelog
(https://modelcontextprotocol.io/specification/2026-07-28). Where the briefing
that kicked off this doc was imprecise, the correction is noted.

| Change | Normative status | Correction to the briefing |
| --- | --- | --- |
| No `initialize` handshake. Every request carries `_meta` `io.modelcontextprotocol/protocolVersion` and `.../clientCapabilities`; a request missing them is a `-32602` / HTTP 400 | MUST | There is a new mandatory server RPC, `server/discover`, that clients MAY call |
| `Mcp-Session-Id` and protocol sessions removed | Removed | |
| Version negotiation: an unsupported version gets `-32022 UnsupportedProtocolVersion` with `data.supported`. Dual-era clients probe and fall back, and the fallback "MUST NOT be keyed to one specific error code" | MUST / SHOULD | |
| Multi Round-Trip Requests: a server returns `resultType: "input_required"` with `inputRequests` and an opaque `requestState`; the client retries with `inputResponses` | MUST, breaking | MRTR replaces elicitation **and** sampling and roots, but only on `tools/call`, `resources/read` and `prompts/get` |
| `Mcp-Method` on every request; `Mcp-Name` on `tools/call`, `resources/read`, `prompts/get` | REQUIRED | There is also `x-mcp-header` on tool params, which clients MUST mirror into `Mcp-Param-*` headers |
| Cacheable lists: `ttlMs` + `cacheScope` on list results | MUST include | There is no ETag. `listChanged` survives, delivered via `subscriptions/listen` |
| Tasks move to the extension `io.modelcontextprotocol/tasks` (SEP-2663, Final): `tasks/get` polling, `tasks/update`, `tasks/cancel`; `tasks/result` and `tasks/list` are gone | Extension | A server MUST NOT return a task to a client that did not declare the extension on that request |
| RFC 9207 `iss`: clients MUST validate before redeeming the code | Client MUST | Only conditionally required: the AS including `iss` is SHOULD. Reject when `iss` is present and mismatched, or absent while advertised |
| DCR deprecated in favor of CIMD. Order: pre-registered, then CIMD if `client_id_metadata_document_supported`, then DCR, then ask the user | SHOULD | Deprecated, not removed. Earliest removal is a revision on or after 2027-07-28 |
| Sampling, Roots and Logging deprecated | Deprecated | Still functional until at least 2027-07-28. `ping` and `logging/setLevel` were removed outright |
| Also: GET stream and SSE resumability removed, no JSON-RPC batching, cancel on HTTP is closing the stream, credentials MUST be keyed by issuer | MUST | |

The Claude article (https://claude.com/resources/articles/bringing-mcp-2026-07-28-to-claude)
says only that support "is being rolled out across Claude products". It gives
no per-surface breakdown. The Claude Code changelog is concrete:

| Version | Change |
| --- | --- |
| 2.1.81 | CIMD support |
| 2.1.274 | 2026-07-28 negotiation for HTTP servers, with auto fallback; opt out with `MCP_PROTOCOL_NEGOTIATION=legacy` |
| 2.1.292 | 2026-07-28 negotiation for stdio |
| 2.1.295 / 2.1.299 | 2026-07-28 negotiation for claude.ai and cloud connectors |
| 2.1.302 | Tolerates servers that omit `resultType`, `ttlMs` or `cacheScope` |

No Claude surface documents Tasks-extension support.

## Library support (published artifacts, 2026-10-18)

| --- | --- | --- | --- | --- | --- | --- |

Two things matter for the port:

- fastmcp 4's transport is `httpx2`, not `httpx`.
- A 401 surfaces as `mcp.shared.exceptions.MCPError`.

Both were verified in A8.

## Impact by area

### 1. OAuth client and token store (`rote mcp login`, `rote.mcp.auth`, `rote.mcp.tokens`)

**Breaks:** nothing yet. DCR remains available until at least 2027-07-28.

**Gaps against the new spec:**

- **No CIMD.** `build_oauth` passes `client_name="rote"` and no
  `client_metadata_url`. The result: rote registers a fresh DCR client on
  every server, including the three that would accept CIMD (A2).
- **No `iss` validation.** mcp 1.30's OAuth provider has no RFC 9207 check.
  The spec makes this a client MUST, and it is the mix-up-attack defense for
  exactly rote's shape: one client talking to many authorization servers.
- **Credentials are keyed by server name, not issuer.** Minor #9 says
  credentials MUST be keyed by issuer and never reused across authorization
  servers. The token-file contract (v1) stores `token_endpoint` and
  `client_info` but not `issuer`. If a server's protected-resource metadata
  starts pointing at a different AS, rote would offer the old `client_info`
  to the new AS.
- **`ping` no longer starts a login.** `login()` and
  `fresh_access_token()` trigger the OAuth flow with `client.ping()`, but
  2026-07-28 removed `ping`. The fastmcp 4 port (PR #103) switches login to
  `list_tools`. Any other cheap "authenticate me" call has to be a method
  that still exists on both protocol versions.
- **GitHub has no `registration_endpoint`.** mcp 1.30 then falls back to a
  legacy `POST <resource-origin>/register` (A2,
  `https://api.githubcopilot.com/register`), which is not GitHub's
  authorization server at all. The pre-registered `client_id` path in the
  registry is the only working route. The login error should say so instead
  of failing on that guessed URL.

**What CIMD needs from rote that the libraries do not provide:**

- **A hosted metadata document.** It must live at a stable HTTPS URL with a
  path, for example `https://roteskills.com/oauth/rote-cli.json`. The domain
  is already live. It needs `client_id` (equal to the URL), `client_name`,
  `redirect_uris`, `grant_types`, `response_types`, and
  `token_endpoint_auth_method: "none"`. A CLI is a public client, and
  workers-oauth-provider forbids symmetric auth for CIMD clients.
- **A redirect-URI policy for loopback.** fastmcp's callback picks a free
  port when `callback_port` is None. A CIMD AS "MUST validate redirect URIs
  against those in the metadata document", and the spec is silent on loopback
  port wildcarding (RFC 8252 section 7.3 allows any port, but whether a given
  AS honors that for CIMD is per-AS behavior). There are two safe choices:
  - Publish a small fixed set of ports, for example 33418 to 33421, and have
    `rote mcp login` bind the first free one.
  - Confirm per-AS port leniency empirically before relying on it.

  This is the one CIMD question no probe here could answer without
  publishing the document (see the open questions).
- **Ownership of the document.** It is a public artifact on a rote-owned
  domain, and anyone can point an AS at it. The spec notes that CIMD "cannot
  prevent `localhost` URL impersonation", so the trust it adds is the
  consent-screen name and logo, not client authentication. That is still an
  improvement over DCR, where every login mints an anonymous client.

### 2. Emitted Python helper (`rote.mcp._runtime_helper`, DBOS-py, python runtime, eval)

**Breaks:** calls to modern-only servers (A5). Dual-era and legacy servers
work today (A4).

**With fastmcp 4 (`auto`):**

- Modern servers negotiate 2026-07-28 with no handshake (A4b).
  - A fresh legacy connection spends two POSTs on setup: `initialize` and
    `notifications/initialized`.
  - `auto` mode spends one instead, a `server/discover` probe. That probe
    can be skipped with a cached discover result, which the spec suggests
    caching per origin.
- Legacy servers fall back transparently, including GitMCP's sessionful
  2025-03-26 server.
- The helper itself needs three changes:
  1. **401 detection.** `_find_http_401` walks for `httpx.HTTPStatusError`.
     Under fastmcp 4 the same 401 is an `MCPError`, so the walk returns
     `False` and park-on-auth silently degrades into a failed step (A8). The
     match must move to the SDK v2 error shape. The regression test must use
     a real server returning 401, not a mocked exception, or it will keep
     passing against the old type.
  2. **Result payload.** `_result_payload` returns `result.data` first. For
     a tool whose `outputSchema` declares typed properties, fastmcp hydrates
     that into a dynamically generated `types.Root` class that neither
     pickles nor JSON-serializes. A real DBOS workflow fails at the step
     boundary with `PicklingError: Can't pickle <class 'types.Root'>` (A7).
     This bug exists on main today with fastmcp 3.4.9, not just after the
     port. The fix is to prefer `structured_content`, which is plain JSON
     and which the spec now allows to be any JSON value, and to keep the
     text fallback for servers that return neither.
  3. **MRTR in unattended steps.** A 2026-07-28 server may answer
     `tools/call` with `input_required`. The emitted step has no human.
     Initial behavior: raise a named error carrying the server, the tool, and
     the requested input keys. That error must be distinct from auth so it
     does not park on `rote:auth:*`. The natural follow-up is to park on a
     derived topic and resume by replaying the call with `inputResponses`
     plus the echoed `requestState`. `requestState` is opaque and
     integrity-protected by the server, so persisting it in the workflow is
     safe. That durability is exactly what rote's runtimes provide and what
     an interactive client would lack. This is a design door, not phase 1.

### 3. Emitted TS helpers (`_roteMcp.ts` for DBOS-TS and Inngest; the Workers helper)

**Breaks:** modern-only servers. The SDK v1 line has no 2026-07-28 support at
all (A5: `-32022`).

**Migration:**

- Move to `@modelcontextprotocol/client` 2.x.
- **Pass `versionNegotiation: { mode: "auto" }` explicitly.** The v2 client
  defaults to `legacy`. A v2 helper without it behaves exactly like v1
  against a modern-only server (A5, "v2 default (legacy)": `-32022`). A test
  that only checks the import line would pass that broken state, so the e2e
  must hit a modern-only server.
- The refresh-grant path (plain `grant_type=refresh_token` POST to the stored
  `token_endpoint`) is untouched. RFC 9207 applies only to authorization
  responses, and the TS helpers never run one.
- 401 detection (`StreamableHTTPError` vs v2's `SdkHttpError`) needs the same
  real-server regression as Python.
- Workers: v2 ships a `cf-worker` JSON Schema validator, matching what
  rote-cloud already does on v1, so workerd compatibility is not a new risk.
  It still needs the live workerd leg of `test_mcp_park_cf_e2e.py`.

### 4. Park-on-auth (DBOS-py, DBOS-TS, Inngest, Cloudflare)

The mechanism is unaffected. Parking, release channels and portable
serialization do not touch the wire protocol. Only the "is this an auth
failure" predicate changes (sections 2 and 3). That predicate is the single
point whose silent failure would make every parked run look like a crash.

### 5. Compiler live MCP tools (`rote.mcp.live_tools`)

`LiveMcpTools` opens a fresh connection per tool call. On modern servers that
saves one setup round trip per call. It saves both if the discover result is
cached (section 2). The `CALL_TIMEOUT_SECONDS` comment
("a server that accepts the socket without completing the MCP initialize
handshake") becomes era-dependent but stays correct.

`readOnlyHint` gating is unchanged. The spec adds that clients MUST reject
tool definitions with invalid annotations, and SDK v2 does that, so a
malformed server now fails listing instead of slipping through.

`ttlMs` / `cacheScope` let the once-at-startup listing be justified rather
than assumed. No change is needed.

### 6. `eval --run`

Claude Code owns the client. It negotiates 2026-07-28 with fallback since
2.1.274, and `headersHelper` is transport-level, so nothing changes.

One caveat: the baseline is now measured on whichever era Claude Code picks.
The scorecard should record the negotiated version per server, so a
before/after comparison never mixes eras silently.

### 7. rote-cloud (private repo, out of scope for this PR, same findings)

`src/worker/mcp/oauth.ts` is DCR-only and the callback validates `state` but
not `iss`. `src/worker/mcp/client.ts` is TS SDK 1.30, legacy-only.

It is the cleanest CIMD case, with an HTTPS web redirect and no loopback
ports. A document at `https://app.roteskills.com/oauth/client.json` would get
Linear-, Notion- and Sentry-class servers a named client instead of an
anonymous DCR one. Track it in rote-cloud.

### 8. `rote serve` / `rote register`

**Today:** FastMCP 3.4.9 serves the legacy, sessionful protocol. Modern
probes get `400 Missing session ID`. Both modern clients (fastmcp 4 `auto`,
TS v2 `auto`, which is what Claude Code uses) fall back and list tools fine
(A9). So `claude mcp add rote -- rote serve` keeps working.

**After the fastmcp 4 port:**

- **List-changed push needs a rework.** It currently tracks `ServerSession`
  objects in a `WeakSet` and calls `send_tool_list_changed()`. Modern clients
  have no session. They receive `listChanged` over `subscriptions/listen`.
  FastMCP 4.1 registers no `subscriptions/listen` handler. A FastMCP server
  on the modern protocol therefore advertises `tools.listChanged: false`
  unless rote installs the SDK's `ListenHandler` itself. This was reported
  from the fastmcp 4 port (PR #103). I have not reproduced it separately.
  Without that handler and a watcher that publishes through it, modern
  clients silently stop seeing new pipelines. Legacy clients keep the old
  path.
- **`tools/list` must carry `ttlMs` / `cacheScope`.** Because the registry
  can change at any time, use `ttlMs: 0` (or a few seconds) and
  `cacheScope: "private"`, and rely on `listChanged` for push.
  `tools/list` SHOULD also return tools in a deterministic order: sort by
  registry name.

## How this changes the MCP Tasks trigger design

The July plan was: the trigger returns a Tasks handle, the client polls, and
`input_required` maps onto `hitl_gate`. It was deferred for two reasons.
Tasks were an RC, and running triggers as tasks "would tie multi-day workflow
observability to the server process's lifetime". The final extension removes
the second objection, as long as rote does **not** use fastmcp-tasks' engine.

1. **Use rote's own `ServerExtension`, not `fastmcp[tasks]`.**
   - fastmcp-tasks runs the tool body inside its Docket worker, with task
     state in Redis or `memory://`. For rote that duplicates the durable
     runtime and reintroduces the lifetime coupling.
   - fastmcp 4's public `ServerExtension` API (capability, `MethodBinding`s
     for `tasks/get` / `tasks/update` / `tasks/cancel`, a `tools/call`
     interceptor) is enough to implement SEP-2663 directly over the runtime
     backends.
2. **The task id is the workflow handle.**
   - It is a signed, self-describing token: registry entry name, runtime,
     `workflow_id`. `tasks/get` resolves it against DBOS's system database,
     Temporal describe, or a Cloudflare status route, which are the same
     backends `<name>_status` already uses.
   - No server-side task store means a `rote serve` restart mid-run is
     invisible to the client, and `ttlMs: null` (unlimited) is honest
     because the runtime owns retention.
   - Signing matters because the spec treats client-echoed state as
     attacker-controlled. An unsigned id would let a caller poll or signal
     arbitrary workflow ids.
3. **Status mapping:**

   | Runtime state | Task status |
   | --- | --- |
   | enqueued / pending / running | `working` |
   | parked on a `hitl_gate` | `input_required`, with `inputRequests` holding one form-mode elicitation built from the gate's resume-payload contract |
   | success | `completed`, with the result |
   | error | `failed` |
   | cancelled | `cancelled` |

   `tasks/update` with the elicitation response is `DBOSClient.send` on the
   gate topic, the same delivery `<name>_signal` does now, with the same
   allowlist of known gate signals.
4. **Park-on-auth becomes visible to Claude.**
   - A run parked on `rote_auth_status` maps to `input_required` with a
     URL-mode elicitation, or at minimum a status message naming
     `rote mcp login <server>`.
   - That closes the open "park visibility" item for anyone driving rote from
     an MCP client. The release still happens through `rote mcp login`. The
     task only reports it.
5. **The `_status` and `_signal` tools stay.** The extension rule is to
   "revert to core protocol behavior" for a client that did not declare it,
   and no Claude surface documents Tasks support today. The trigger returns
   a task only when the request's `clientCapabilities.extensions` includes
   `io.modelcontextprotocol/tasks`. Otherwise it returns today's
   `{workflow_id, status: "started"}`.
6. **Modern-only.** The extension is negotiated per request in the modern
   era, so legacy clients never see it. That is consistent with the rule
   above and needs no special case.

This design depends on the fastmcp 4 port landing first, and it is worth
building before any Claude client consumes it: fastmcp 4's own client polls
tasks transparently, so it is testable end to end with no inference.

## Migration options

### Option A: dual-stack (recommended)

| Area | Change |
| --- | --- |
| Python wire | fastmcp 4 `auto` everywhere (helper, live tools, `rote mcp login`); fix 401 detection and result payload |
| TS wire | emitted helpers on `@modelcontextprotocol/client` 2.x with explicit `mode: "auto"` |
| Registration | registry pre-registered `client_id` first, then CIMD via a published `rote-cli.json`, then DCR fallback |
| `iss` | inherited from mcp 2.x |
| Token file | contract v2 adds `issuer`; readers accept v1 |
| `rote serve` | modern + legacy, list-changed via `subscriptions/listen`, then the Tasks extension as a follow-up |

- **Pros:** works against every server class probed. That covers
  modern-only (A5), dual-era, legacy-sessionful (GitMCP), CIMD (Linear,
  Notion, Sentry), DCR-only (Atlassian, Cloudflare, Stripe, Supabase,
  Vercel, Figma, Zapier), and pre-registration (GitHub, Asana, HubSpot). It
  closes the `iss` MUST. Most of it rides on the fastmcp 4 port already in
  progress.
- **Cons:**
  - The fallback is a probe, which costs one extra round trip per new
    connection on legacy servers. Caching by origin, as the spec suggests,
    removes it.
  - The CIMD document becomes a hosted dependency of the CLI login, with a
    redirect-port policy to settle.
  - It covers two eras until DCR and the legacy handshake are actually
    removed, at the earliest 2027-07-28.

### Option B: CIMD-only registration, modern-only wire

- **Pros:** one code path; no anonymous DCR clients.
- **Cons:** fails today. CIMD-only breaks login on 8 of 14 probed
  authorization servers, and modern-only wire breaks DeepWiki and GitMCP
  (A1, A3). Not viable before the 2027 removal window, and even then it
  depends on server adoption.

### Option C: wait (stay on fastmcp 3 and TS SDK 1.x)

- **Pros:** zero work now. Everything probed works.
- **Cons:**
  - rote ships a client that violates a 2026-07-28 MUST (`iss`) against the
    eight probed authorization servers that advertise it.
  - It breaks with an opaque 400 the first time any server rote binds to
    goes modern-only. The TS SDK 2.x `createMcpHandler(..., { legacy:
    "reject" })` makes that a one-line choice for server authors.
  - It holds the Tasks trigger hostage to an old FastMCP.
  - The pinned versions also stop receiving the security fixes the v2 lines
    get.

**Recommendation: A.** Sequence it as:

1. The two defect fixes. Both are in the fastmcp 4 port (PR #103). The
   `Root` pickling one also affects main today, so it should not wait on
   the rest of the port.
2. fastmcp 4 port, with the era matrix.
3. TS v2 helpers.
4. CIMD document, `issuer` field, and the login change.
5. `rote serve` list-changed and cache fields.
6. The Tasks extension.

## Test plan (no inference anywhere)

Everything below is a test in the CLAUDE.md sense: real servers and
toolchains, stubbed only at the browser and the LLM. The third-party probes in
the appendix are deliberately **not** tests, because they hit servers rote
does not control. They are a rerunnable battery for checking the ecosystem
before a release.

1. **Era matrix**, new and parametrized.
   - Server side: three local fixtures.
     - modern-only: TS v2 `createMcpHandler(..., { legacy: "reject" })`, as
       in A5;
     - dual-era: fastmcp 4 default;
     - legacy-sessionful: fastmcp 3 or TS v1 with a `sessionIdGenerator`.
   - Client side: each emitted runtime client. That means the Python helper
     (`test_mcp_e2e.py`), `_roteMcp.ts` (`test_mcp_ts_e2e.py`), and the
     Workers helper inside workerd (`test_mcp_park_cf_e2e.py`).
   - Assert the call succeeds **and** the negotiated version, so a client
     that silently stays legacy against the dual-era fixture fails.
   - Negative half: `mode: "legacy"` against modern-only must fail, which
     proves the fixture is really modern-only.
2. **401 to park, under the new SDKs.** Extend `test_mcp_park_e2e.py`,
   `test_mcp_park_ts_e2e.py`, `test_mcp_park_inngest_e2e.py` and
   `test_mcp_park_cf_e2e.py` so the 401 comes from a modern-era server.
   - Verify the test by reverting the predicate fix and watching it fail.
     That is the A8 failure.
3. **Typed output schema survives a durable step.** A fixture tool with a
   typed `outputSchema` through a real DBOS workflow (the A7 repro as a
   test). Assert the step result equals the plain dict, and that it
   pickle-round-trips.
4. **OAuth registration order**, extending `test_mcp_oauth_e2e.py`. Four
   in-memory AS variants:
   - CIMD-advertising: assert the authorize request's `client_id` is the
     CIMD URL and that no registration POST happened;
   - DCR-only: assert a registration POST and a minted `client_id`;
   - pre-registered: the registry `client_id` wins even when CIMD is
     advertised;
   - neither: the error names `rote mcp add --client-id`.

   The SDK requires an HTTPS `client_metadata_url`, so the fixture serves the
   document over local TLS (a `trustme` CA) rather than relaxing the check.
5. **`iss` validation.** The AS fixture returns:
   - a mismatched `iss`, which must be rejected before any token request;
   - no `iss` while advertising support, which must be rejected;
   - no `iss` while not advertising, which must proceed.

   Assert on the absence of a token-endpoint hit, not just on the error.
6. **Issuer keying.** The protected-resource metadata switches to a second
   AS between logins. The stored `client_info` must not be offered to the
   new issuer.
7. **`rote serve`, both eras**, extending `test_serve_server.py` /
   `test_dbos_serve_e2e.py`:
   - fastmcp 4 `auto` and a legacy client both list tools;
   - `tools/list` carries `ttlMs` and `cacheScope` and returns sorted tools;
   - a registry write reaches a modern client's `subscriptions/listen`
     stream and a legacy client's `list_changed`.
8. **Tasks extension**, extending `test_dbos_serve_e2e.py`. A fastmcp 4
   client declaring the extension triggers a pipeline with a HITL gate, then:
   - gets `resultType: "task"`;
   - polls to `input_required`;
   - answers via `tasks/update`;
   - polls to `completed`;
   - **restarts `rote serve` mid-run** and keeps polling the same task id,
     which proves there is no server-side state;
   - tampers with the task id and is rejected.

   A client *not* declaring the extension gets today's `workflow_id`
   response from the same tool.

### A2. Which registration path `rote mcp login` takes (no side effects)

`$MAIN/bin/python -I $P/probe_login_path.py linear=https://mcp.linear.app/mcp atlassian=https://mcp.atlassian.com/v1/mcp cfbindings=https://bindings.mcp.cloudflare.com/mcp github=https://api.githubcopilot.com/mcp/`

The probe runs rote's real `build_oauth` with two independent guards:

1. **Allowlist.** It first discovers each server's advertised
   `registration_endpoint` with its own GETs. During the run, an httpx hook
   lets through only GETs and the POST to the MCP endpoint itself. Every
   other request is aborted before it is sent. Each blocked request is
   classified as DCR at the advertised endpoint, DCR at a guessed endpoint,
   or unexpected.
2. **Redirect intercepted.** The authorization redirect is printed and
   never opened, so the flow cannot reach a token request.

A registration endpoint at an unusual path is therefore still blocked. I
checked the guard directly: a POST to `/oauth/clients` (as an advertised
endpoint), a POST to `/token`, and a PUT or DELETE to the MCP URL are all
blocked, while discovery GETs and the MCP-endpoint POST pass.
